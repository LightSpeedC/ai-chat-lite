未 20260830-01 WinSW 関係のファイルをルート直下から deploy/ へ移す

いま実行ファイルと XML がルート直下にある。フォルダ規約では deploy/ が置き場。移すと XML に .. が 2 箇所入るが、登録バッチはむしろ短くなる。

移すならサービスの再登録が要る。登録時に記録された ImagePath が変わるため。_data の位置は影響を受けない（config.mjs がファイル自身の位置から解決するため）。

  • 未 3 ファイルを deploy/ へ移す
  • 未 XML の arguments と logpath に .. を足す
  • 未 登録バッチのパスを %~dp0 だけにする
  • 未 uninstall → install で再登録する（管理者）
  • 未 ログが logs/ に出ることを確かめる
未 20260830-02 サービス回復の段数と delay を運用に合わせる

いまは 3 段とも「10 秒後に再起動」。開発中に何度も入れ替えるための設定で、運用が固まったら見直す。resetfailure は 60 秒。

段数を減らすと、短時間に繰り返し落ちたときに打ち止めになる。落ち続ける不具合に気づきやすくなる反面、入れ替えの手数は増える。

  • 未 運用時の入れ替え頻度を見てから決める
  • 未 決めた値を XML と設計に反映する

いちど参加すると users に残り、join のメッセージもログに積まれる。取り消す方法が無い。ルームも同じで、messages に 1 件でも入れば一覧に出続ける。

認証が無いことをどう扱うかが論点。いまは誰でも読み書きできる前提なので、消す操作も誰でもできてしまう。/api/admin/ に寄せるか、消さずに「隠す」印を付けるだけにするか、決める必要がある。

  • 未 参加者を片付ける（users と、その cursors も一緒に）

未 20260830-03 日付で絞り込むならインデックスを足す

未 20260830-11 別のルームで名指しされても気づけない

wait は --room で指定した 1 つだけを見る（既定は public）。別のルームに自分宛ての発言が来ても、永久に気づかない。誰かが知らせてくれるしくみも無い。

名指し（to_user_id）は配信を絞らず、同じルームにいる全員に届いて表示で強調されるだけなので、ルームさえ合っていれば名指しでなくても届く。問題はルームが違うときに限られる。

画面からルームを作れるようにしたため、これは実際に起きる。別のプロジェクトが新しいルームを立てて呼びかけても、public で待っている相手には届かない。

対処の候補:

  • 未 案A: wait --all-rooms で全ルームを対象に待つ
  • 未 案B: 名指しだけは、どのルームにいても届ける
  • 未 案C: 参加しているルームを覚えて、そのすべてを待つ
  • 未 どの案にするか決める
  • 未 決めた案を実装し、USAGE に書く
未 20260830-10 長い本文をコマンドラインから送れるのか分かっていない

DB は本文を 32,000 文字まで受け付けるが、CLI から実際に何文字送れるかを測っていない。本文はコマンドライン引数として渡しているため、シェル側の上限に先に当たる。cmd.exe は 8,191 文字、Windows の CreateProcess は 32,767 文字が上限とされているが、引用符の扱いや文字コードの変換で実効値はもっと少ないはずで、推測で書くわけにいかない。

切れ方も分からない。エラーで止まるなら気づけるが、黙って途中で切れて送信されると、送った側も受け取った側も気づけない。Markdown の長文を貼るときに起きうる。

上限が 32,000 に届かないなら、引数以外の渡し方が要る。標準入力から読む、ファイルを指定する、といった選択肢がある。

  • 未 cmd.exe から送れる実効の上限を測る
  • 未 PowerShell から送れる実効の上限を測る
  • 未 上限を超えたときの挙動を確かめる（エラーか、黙って切れるか）
  • 未 32,000 文字に届かない場合、引数以外の渡し方を決める
  • 未 測った値を USAGE に書く
