<strong>i260920-01 (初回のカーソル起点)を実装・コミットしたが、本番サーバー (Windowsサービス)は再起動されず、2026-09-20 17:21 に起動したプロセスがそのまま動き続けていた。</strong>Node.js はファイルを更新しても再起動しない限り古いロジックのまま動くため、サーバー側の変更 (i260920-01・i260907-04 等)が本番で一度も有効になっていなかった (i260922-03 の調査中に発見)。

> [!IMPORTANT]
> <strong>API はエラーにならない。</strong>この種の変更 (サーバー内部ロジックだけを変え、リクエスト・レスポンスの形は変えない)は、古いサーバーに新しい CLI から繋いでも普通に 200 が返る。**クライアント・サーバー間のバージョン不一致を検出する仕組みがこのプロジェクトに存在しない**ため、実測 (本番へ直接 `wait` して`since`の値を見る)でしか気づけなかった。

版が別々にある仕組みは既にある (ブラウザ向け `VERSION`・CLI突き合わせ用 `EXPECTED_SCHEMA`)が、どちらも「サーバー再起動忘れ」を検出する用途ではない。サーバーの版とクライアントの版を記録し、**クライアントが要求する最低サーババージョン、およびサーバーが要求する最低クライアントバージョンの双方を判定し、満たない側はエラーにする**仕組みが要る。

恒久対策 (版の不一致検出)とは別に、**引数の過不足チェック**(未知のパラメータ・必須パラメータの欠落を API が 400 で拒否する)も暫定対策として有効。ただし今回のケース (`messages` を返す形自体は変わらず、CLI側が表示しなかっただけ)のように、**パラメータの形が変わらない変更では引数チェックでは検出できない**。カバーできる範囲が違うため、両方を課題として残す

- [未] 実装し、node版・Rust版とも対応する
- [未] API に引数の過不足チェック (未知パラメータの拒否・必須パラメータの欠落判定)を追加する (暫定対策。版の不一致そのものは検出できない点に注意)
