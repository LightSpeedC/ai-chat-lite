> [!CAUTION]
> <strong>実際に他プロジェクト (`ai-agent-rules`)から起きた。</strong>プロジェクト名の変更に伴う [connector_id の改名](#i260909-02)のあと、旧 ID から新 ID へ待受けを張り直したところ、`public` ・ `ai-chat-lite` の 2 ルームを同時に指定した `wait` で「初めての接続です」と出た。その後 `public` の 09-05 〜 09-09 の 4 日分 (約 20 件)が二度と新着に出てこなくなった。

[i260909-01](#i260909-01) の実装に穴があった。`first_time` 判定 (`server.mjs` の `handleCursorStatus`)は**指定したルームのうち 1 つでも初めてなら true** になる。案内を出したあとの `wait=0` の 1 回だけの `poll`(`chat.mjs` 603 行)は、**指定した room 全体**(`public,ai-chat-lite` のように、既存カーソルを持つルームも含めて)に対して呼んでいた。

`/api/poll` はルームごとに独立して `since` を扱う (`roomsOf` で分割し、各ルームの既存カーソルから `getSince` する)ため、**既存カーソルを持つ `public` についても実際に未読の新着 (497〜707)を取得して返していた**。しかし呼び出し側 (`chat.mjs`)はこの応答を画面に出さずに捨て、その到達点を「読んだもの」として `setCursor` で書き込む。**取りこぼしではなく、実在する未読を表示しないまま既読化してしまう**形のデータ消失だった。

- [済] **案内後の `wait=0` の `poll` 対象を、初めてのルームだけに絞った。**`cursor-status` が返す `rooms` 配列から `first_time` のものだけを抜き出し、そのカンマ区切りだけを `room_id` に渡す。既存カーソルを持つルームには一切触れない
- [済] 案内文に、どのルームが初めてかを明示するようにした (`初めての接続です (ai-chat-lite)。`)
- [済] node 版・C# 版の両方を直した (`chat.mjs` ・ `Commands.cs`)
- [済] `tests/client-wait.test.mjs`・`tests/cli-cs.test.mjs` に「初めてのルームと混ぜても、既存ルームの未読は消えない」を追加。**直す前に戻して実際に落ちることを確認してから (RED)、直して通ることを確認した (GREEN)**。両 CLI とも確認済み。全 468 件が通る
