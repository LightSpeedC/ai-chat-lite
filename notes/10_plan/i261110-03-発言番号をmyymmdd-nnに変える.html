番号の仕様

形: m + yymmdd + - + nn。日付は sent_at の日 (JST)。nn はその日の何件目かで、1 件目から振る。例: m261117-01。

nn に使う 35 字 (40-A)

0123456789abcdefghijkmnopqrstuvwxyz (数字 10 字と、l を除く小文字 25 字)。順は、文字コードの順と同じ (数字が先、英字が後)。大文字は使わない。

桁の伸び方 (39-A)

桁形範囲の件数最初と最後
2先頭が z 以外の文字 + 任意の 1 字1,18901 〜 yz
4z + 先頭が z 以外の 3 字41,650z000 〜 zyzz
6zz + 先頭が z 以外の 4 字1,457,750zz0000 〜

以降も同じ。「先頭の z の数 + 2」が桁数になる。例: 1 → 01 ・ 10 → 0a ・ 20 → 0k ・ 21 → 0m (l を飛ばす) ・ 34 → 0z ・ 35 → 10 ・ 70 → 20 ・ 1,189 → yz ・ 1,190 → z000。

測った値 (2026-11-17、dump): 発言 1,673 件 ・ 76 日分。最多は 2026/09/07 の 70 件で、2 桁に収まる。msg_seq の順に並べて sent_at が戻る箇所は 0 件なので、日付と日内の順を msg_seq から作り直せる。

守る性質 (総当たりの試験)

  • 一意: 1 から 200 万まで、番号が重ならない
  • 順序: 文字列の順が、件数の順と同じ。長さが混ざっても崩れない (yz < z000、zyzz < zz0000)
  • 逆変換: 番号から件数に戻せる。l ・ 大文字 ・ 桁数が偶数でないものは、番号として受けない

DB の変更

新しい版 (ver_000008) を足す。当て済みの版は書き換えない。起動時に自動で当たり、版を上げる前の控えは migrate.mjs が自動で取る。下りは持たない (戻すときは控えから)。

順内容理由
1messages に msg_id TEXT を足す。CHECK (msg_id IS NULL OR length(msg_id) BETWEEN 10 AND 32)人に見せる番号。msg_seq は内部の並びと読み位置のために残す (41-A)
2日ごとの連番の台帳 message_day_counters を作る (message_day = yymmdd が主キー、last_count)。STRICT行を数えて 1 を足すと、行が無くなったときに番号が重なる。台帳なら、増える一方で重ならない
3今ある全行に msg_id を振る。ROW_NUMBER() OVER (PARTITION BY substr(sent_at, 1, 10) ORDER BY msg_seq) を、35 字の並びから 2 桁に直す42-A。SQL だけで書く (版の仕組みは .sql しか当てない)。今ある日の最多は 70 件なので 2 桁で足りる
42 桁 (1,189 件) を超える日があれば、版ごと失敗させる。CHECK (rn <= 1189) を付けた一時テーブルへ先に写して確かめる黙って欠ける番号を作らない。超えた日が出たら、そのとき計画を見直す
5message_day_counters に、日ごとの件数を入れる起動後の最初の発言が、続きの番号から始まるように
6一意索引 messages_ix_msg_id (msg_id)重なりを DB が止める。UNIQUE は ALTER では付けられないので、索引で付ける

NOT NULL にできない。既存の表に列を足すとき、NOT NULL は既定値が要る。表を作り直せば付けられるが、1,673 行の写しと索引の張り直しが要り、リスクのほうが大きい。代わりに、発言を足す処理 (store.mjs の insertMessage の 1 か所) が必ず msg_id を書き、「msg_id が NULL の行が 0 件」を試験で守る。

発言を足す処理

insertMessage を、1 つのトランザクションにする。(1) 台帳の last_count を 1 進めて新しい値を受け取る (INSERT … ON CONFLICT DO UPDATE … RETURNING)。(2) その値から nn を作る (src/server/msg-id.mjs)。(3) msg_id を付けて messages へ書く。片付け ・ 戻すは行を消さないので、msg_id は片付けても戻しても変わらない。

版を当てたあとの確かめ (試験。本番の控えのコピーで流す)

  • 行数が変わらない。msg_id が NULL の行が 0 件。msg_id が一意
  • 日ごとに、msg_seq の順と msg_id の順が同じ
  • 台帳の last_count が、日ごとの件数と一致する
  • 起動後の最初の発言が、その日の続きの番号になる。日が変われば 01 から始まる

切り替えの手順

順序が要点。サーバーを先に新しくし (古い CLI はそのまま動く)、そのあとで CLI を新しくする。逆にすると、新しい CLI が msg_id を持たない応答を受ける。

順すること指示
1落ちる試験を先に書き、❌Red を確かめる (nn の総当たり ・ 版 8 の移行を控えのコピーで ・ API ・ CLI の出力と入力 ・ 突き合わせ)承認後
2msg-id.mjs ・ ver_000008 ・ store.mjs ・ server.mjs を作る承認後
3CLI を node 版 ・ Rust 版に入れ、突き合わせる。Web を直す承認後
4資料を直す。全件の試験 (psh 経由の node と、bun) を流す承認後
5周知の予告案を出す (表示が変わる日と、出力の #番号 を読んでいる道具の申告のお願い)「送って」
6サーバーを起動し直す (版 8 が当たる。控えは自動)。確かめ: 本番の dump で、msg_id が NULL の行が 0 件、日ごとの順が同じ「起動し直して」
7Rust 版を作り直し、既定の aichat.exe へ写す。写した瞬間から、全プロジェクトの出力が新しい形になる「写して」
8共通ルールの差し替え案 (暫定の行 → msg_id の書き方) を差分で出し、周知案を続けて出す「反映して」「送って」
9ai-agent-tools へ issue --refs の依頼を出す。課題 i261110-03 を、依頼元の確認が取れたら済にする「送って」

リスクと確かめ

リスク対策
全セッションの出力が一斉に変わる (既定の exe を写した瞬間)写す前に周知する (手順 5)。写しは指示を待つ。サーバーが先に新しくなっているので、写す前の古い CLI も動く
出力の #番号 を正規表現で読んでいる道具が、読めなくなる周知で申告を求める。他プロジェクトの中身は、こちらから見ない (ai-agent-tools への依頼は、issue --refs だけ)
msg_seq と msg_id の取り違え入力の判定は形で決める (m + 6 桁 + - + nn なら msg_id、数字だけなら msg_seq)。試験で、両方と、どちらでもない値を確かめる
本番の DB を変える版を上げる前の控えは自動。控えのコピーで、版 8 を先に流して確かめる。-wal ・ -shm は 3 つ一組で扱い、元の置き場を増やさない
日をまたぐ時刻 (JST 0 時)日付は sent_at の日で決める。台帳の日と、行の日が食い違わないよう、同じ値から作る
1 日が 1,189 件を超える4 桁に自動で伸びる (z000〜)。今の最多は 70 件。版 8 の移行だけは、超えると失敗する (手順 4 の確かめ)
